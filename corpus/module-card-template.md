# Module case study

Record module ID, scientific topic, source root, source revision, reviewed file hashes, review date, reviewer, review status, and license verification status. Register sources in `catalog.json`; do not imply a module is validated merely because it has an entry.

## User task and scientific output

Describe audience, learner question, inputs, preprocessing, algorithm, outputs, and scientific limitations.

## Source-backed patterns

For each relevant area (HTML/CSS layout, Bokeh layout, controls, computation, session state, diagnostics, learning content, tests, startup), record source paths, observed behavior, reuse opportunities, and limitations. Distinguish source inspection from browser observations.

## Adaptations for future modules

Explain which patterns transfer and when they should change. Include known defects or scaling limitations rather than treating the module as an unquestioned ideal.

## Feedback and promotion

Record feedback with evidence, proposed change, reviewer, and status. Preserve the original observation when updating the card. Require human review before changing an entry from source-reviewed to approved-exemplar. Model quality depends on both the supplied examples and the underlying model's reasoning; a corpus entry does not guarantee better output.
