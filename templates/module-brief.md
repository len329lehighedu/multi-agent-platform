# Module brief

## Request and audience

Record the user's original request, module ID, audience, prerequisites, and learning objectives. Distinguish explicit requirements from proposed defaults.

## Scientific contract

Specify the question, desired output representation, scientific assumptions, input schema and units, example data, valid ranges, preprocessing, split requirements, and correctness oracle. For equation discovery, specify symbolic expression versus numerical model and what recovery means.

## Learner experience

Describe inputs/controls, interactions, plots, output interpretation, errors, assessment, and presentation preferences. List exemplar modules to inspect without requiring a literal clone.

## Execution constraints

Record supported environment, CPU/GPU availability, dataset limits, training budget/stopping behavior, responsiveness expectations, allowed dependencies, run resource budget, and repair limit. Label unmeasured runtime estimates.

## Acceptance criteria

For each criterion: ID, required behavior, verification method, mandatory/optional, and responsible role. Include scientific, interaction, instructional, setup, and performance criteria proportional to the request.

## Assumptions and unresolved issues

Record assumptions with rationale and identify questions that block correctness or scope. Do not leave critical output semantics implicit.
